# 对话与后台诊断衔接

2026-11-16 实现说明。对话先读当前 Incident、告警、样本与服务日志、规则归因和已有分析；复杂调查交给现有 Incident 分析 worker，提交任务后继续回答，不等待 worker 完成。不新增队列或中间件，仍使用 PostgreSQL 分析记录、Modulith 事务事件和 Kafka 派发。

## 分支与授权

| 当前情况 | 对话行为 |
|---|---|
| 最新请求已完成，覆盖当前告警到达时间 | 把后台分析作为参考，与本轮原始证据对照回答；可以用只读工具补查 |
| 只缺工具可直接获取的数据 | 使用 `search_logs`、`count_logs`、`get_incident` 等原有只读工具 |
| 复杂调查或现有分析不适用 | 模型可以调用 `delegate_diagnosis(incident, reason)`；限本轮已经读取的事件，服务端决定提交或复用 |
| 已有 pending | 复用任务，显示“等待或执行中”；不再提交第二份任务 |
| 同批告警证据已有 completed / failed / timed_out | 不自动重跑；失败不等于系统正常。继续补查，需要重跑则提出确认卡片 |
| 未形成 Incident，或没有告警/样本及相关错误日志 | 明确说明当前证据不足，不为此盲目提交诊断。分析不会自动创造新证据 |
| 用户明确要求重新分析 | 保留 `request_analysis` 操作卡；确认后才请求人工重新分析 |
| 改状态、启动容器、结束事务、修改开关 | 保留原有卡片、版本/摘要校验及执行回执，不获得额外自动权限 |

没有对话模型时，只有一个明确事件、存在告警及样本或相关错误日志、没有适用后台结果且未匹配到 Runbook，编排才尝试受限调度。匹配 Runbook 后继续走现有只读探针和确认卡片。关闭证据预取的实验分支不提供委托工具，因为尚未建立本轮委托范围。

这里的系统调度只写“只读诊断的任务记录”，worker 本身仍只能读数据；它与用户主动强制重跑的 L1 操作卡分开。该例外不放开任何运维写操作，也不把模型的建议当作用户确认。

## 服务端去重与证据时效

- 新增 `POST /api/v1/incidents/{id}/analyses/ensure`：202 返回实际复用或创建的分析；204 表示无告警事件、事件已结束或自动次数已达上限；404 为事件不存在。202 也可能返回已完成或失败的原任务，不能把 HTTP 202 当成任务仍在执行。
- `Analyses.ensure` 和原有人工请求在同一 Incident 的 PostgreSQL 事务级 advisory lock 下运行；原有“每事件最多一个 pending”的唯一索引继续兜底。扫描器也复用 `ensure`，避免扫描、不同会话与模型轮次各自创建任务。
- 先复用 pending；否则比较最新任务的 `requested_at` 与时间线 `OPENED/ALERT_ATTACHED` 的最新到达时间。同批证据已有终态记录也复用，只有后续新告警到达才允许新自动尝试。继续受 `max-auto-analyses` 限制。
- 使用告警**到达**时间，避免晚到但事件时间较旧的告警被误判为已分析；状态流转本身不视为新证据。对话兼容缺少时间线的旧数据时退回 `stored_at` 或 `last_alert_at`；前端没有时间线时退回 `last_alert_at`。
- 对话只把同一 Incident 最新**请求**且覆盖当前告警证据的 completed 结果放入 `background_analysis`。较早任务的迟到完成不会顶替新任务；陈旧结果只作为任务状态出现，不把摘要作为当前结论交给模型。
- 后台假设的引用只映射本轮实际读取过的证据编号；历史会话中曾经读取过的引用不会因此被当作本轮已读取。
- 每轮还缓存一次委托的结果，包括请求失败或回执丢失；不会因为模型重复调用而重发。不匹配事件的回执不展示为成功。

## 展示与结果衔接

SSE 新增 `analysis` 事件，包含 `incident_id`、`incident_ref`、`analysis_id`、实际 `status`、请求时间、证据到达时间和 `stale`。Recorder 把它保存在回答的 `trace.analyses` 中，重载会话后继续按原任务查询。人工确认重新分析成功的回执也生成同样的任务卡，未确认的卡片不会生成后台任务。

任务卡使用现有 `usePolling`，页面可见且任务 pending 时每 3 秒只读查询；完成/失败/超时后停止，查询出错显示错误并等待手动刷新，卸载后不更新界面。状态契约只有 `pending/completed/failed/timed_out`，没有可靠的 worker 开始时间，所以 pending 写“等待或执行中”，不虚构 running。

查询使用 `GET /analyses/{analysis_id}`，同时核对事件身份、事件最新请求及最新告警到达时间。旧任务的迟到结果显示“历史结果”，不会替换新任务。完成后卡片展示摘要、原因假设、置信度、可点开的证据和未通过校验的引用数量；用户点击“结合当前证据解释”会正常发起新一轮对话，重新预取当前证据后解释。

## 已知限制与指标

- 不自动追加一次大模型回答；后台完成后的即时呈现是结构化任务卡。更完整的对照解释由上述按钮或用户追问触发。浏览器关闭时不推送通知，重新打开后按任务 ID 查询。
- 终态卡片展示最近一次核对时间；终态后不持续轮询，后续新任务/新告警需手动刷新或新一轮对话核查。卡片不宣称这份结果永久最新。
- 时效判断以告警到达时间为边界，不是全量日志快照或证据内容哈希。只增加服务日志、没有新告警时，不会自动反复启动新任务；同批证据结果不适用时优先只读补查或由人确认重新分析。
- 后台分析的取证、工具预算、超时与证据校验保持现有机制；重新分析不能保证获得额外证据或正确根因。
- 本次没有重新测量延迟。`first_event_ms` 是对话首个事件，`first_answer_ms` 是答案文字首字；任务耗时仍来自后台结果的 `duration_ms`。诊断进度卡不计为答案首字。`project-design.md` 中 3.1 s → 1.4 s 是旧的证据预取实验：两边均关闭深度思考、mysql-down、每方案 2 问 × 3 轮 = 6 个回答、不含浏览器 HTTP 跳转；不能当作本功能的后台完成时间或新性能结果。
